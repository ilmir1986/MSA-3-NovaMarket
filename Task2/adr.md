### <a name="_3bfxc9a45514"></a>**Функциональные требования**

| № | Действующие лица или системы | Use Case | Описание |
|:-:|:-|:-|:-|
| 1 | Покупатель | Просмотр списка заказов | Отображение всех заказов с датой, суммой, способом доставки и статусом |
| 2 | Покупатель | Просмотр деталей заказа | Отображение состава заказа (товары, количество, цена), способа оплаты/доставки, финального статуса |

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**

| № | Требование |
|:-:|:-|
| 1 | Время отклика: <1 секунда (99.99%), ≤0.3 секунды (98%) |
| 2 | Поддержка нагрузки до 40 000+ заказов/день в финальном состоянии |
| 3 | Масштабируемость: возможность добавления новых атрибутов без изменения основных сервисов |
| 4 | Согласованность: данные должны быть актуальными (eventual consistency допустима) |

### <a name="_qmphm5d6rvi3"></a>**Решение**

Выбран **CQRS + Event Sourcing** подход:

- **Write Side**: существующие микросервисы (`order`, `inventory`, `payment`, `delivery`) продолжают работать как есть, публикуя доменные события.
- **Read Side**: внедрён новый **Order View Service** — read-only микросервис, который:
    - Подписывается на все релевантные события через Kafka
    - Строит и поддерживает денормализованную проекцию заказа в собственной PostgreSQL БД
    - Предоставляет единый endpoint `/orders/{id}` и `/orders?userId={id}` для фронтенда

**Логика выбора:**
- **Скорость ответа**: фронтенд получает все данные одним запросом → удовлетворяет требованиям latency
- **Масштабируемость**: read-model можно масштабировать независимо от write-side
- **Слабая связанность**: основные сервисы не изменяются, новые данные легко добавляются в read-model
- **Совместимость**: полностью соответствует уже реализованной Saga-хореографии

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

| Подход | Плюсы | Минусы |
|:-|:-|:-|
| **API Composition** (фронтенд вызывает все сервисы) | Простота, нет дублирования данных | Нарушает latency-требования (N+1 запросов), высокая нагрузка на клиент, сложная обработка частичных сбоев |
| **Shared Database** (все сервисы пишут в одну БД) | Простой JOIN, быстрый ответ | Нарушает принцип автономности микросервисов, создаёт жёсткую связанность, невозможна независимая эволюция схем |
| **Backend for Frontend (BFF)** без CQRS | Централизованная логика агрегации | По-прежнему требует N вызовов к сервисам → не укладывается в latency, сложная обработка ошибок |

### **Недостатки, ограничения, риски**

1. **Eventual consistency**: данные в истории могут отставать на несколько секунд от реального состояния.  
   *Митигация*: показывать timestamp последнего обновления; для критичных операций (чек) использовать прямой вызов `payment`-сервиса.

2. **Дублирование данных**: увеличение storage cost.  
   *Митигация*: данные read-model компактны (только для отображения), хранятся в отдельной БД.

3. **Сложность восстановления**: при потере данных read-model требуется перестроить из событий.  
   *Митигация*: использовать Kafka с длительным retention + snapshot-механизм.

4. **Дополнительный сервис**: увеличение operational complexity.  
   *Митигация*: Order View Service stateless, легко деплоится в Kubernetes, мониторится через Actuator + Micrometer.
